# 팀원용: 평가 DB와 질문 파일 만들기

이 문서는 다른 학교 DB에 대한 적응성을 평가하려고, 팀원이 평가용 DB와 질문을 만드는 방법이다. 규칙은 2026-10-01 사용자 결정(ADR-086, [human-validation-checkpoints.md](human-validation-checkpoints.md))을 따른다.

## 1. 지켜야 할 것

1. 다른 대학의 공개 수강편람·시간표를 참고해 **흉내 낸** DB를 만든다. 학교명과 교수명은 지어낸다.
2. 질문과 정답은 **DB를 만든 사람이 먼저** 정하고 고정한다.
3. 개발자(AI 포함)는 평가 전까지 그 DB와 질문을 **보지 않는다**. 질문 파일을 채팅이나 저장소에 올리지 않는다.
4. 첫 실행 결과는 그대로 남는다. 그 뒤 고친 결과는 "재실행"으로 따로 기록된다.

## 1-1. 내 PC 환경 점검

저장소 루트에서 아래 명령을 실행한다. 빠진 것과 해결 방법을 줄마다 보여 준다. 접속 정보와 비밀번호는 출력하지 않는다.

- 이 명령의 통과는 L7(재현성) 통과가 아니다.

## 2. DB 만들기 (PostgreSQL)

- 합성 DB(`schema_adaptive_synthetic`)에 학교마다 schema를 하나 만든다(예: `school_a`). 레거시 DB에는 만들지 않는다.
- table·column 이름은 그 학교 자료에 맞게 자유롭게 짓는다. 한 table이어도, 여러 table이어도 된다.
- 과목 코드(학수번호)는 꼭 있어야 한다. 채점에 쓴다.
- 학점·정원·수강 인원·대상 학년 같은 숫자 칸은 `integer`나 `numeric` 형식으로 만든다. 글자 칸은 정해진 변환이 있어야 게시할 수 있고, 직접 만든 도메인 형식은 막힌다. 학점 `3/3/0`은 지원하지만 `3-2-2`는 지원하지 않는다.
- 공통 항목은 ontology v3이다. **개설 연도는 사용 중단**했다(ADR-101). DB에 연도 칸이 있어도 질문 항목이 아니다. 학기는 그대로 쓴다.
- 이번 개발에서 확인한 형식은 다음과 같다(8-21). 그 밖의 형식도 괜찮고, 그런 형식에서 적응성을 보는 것이 평가의 목적이다.
  - 넓은 단일 table
  - 공통코드 table
  - 교시 번호 시간표
  - 한 칸에 묶인 시간표

## 3. 화면에서 등록·검토·게시

1. `backend/.env`에 `PG_SOURCE_<이름>=<합성 DB DSN>`을 넣고 `npm run dev:all`로 켠다.
2. 메인 화면의 **DB 변경**을 누른다. 탭은 **사용할 DB / DB 등록 / 검토·게시** 세 개다.
3. **DB 등록**에서 **연결**, **테이블 묶음(schema)**을 고르고 **DB 식별자(ID)**와 **표시 이름**을 넣어 **등록**한다.
   - ID: 영문 소문자·숫자·하이픈만, 첫 글자는 영문 소문자나 숫자, 1~64자. 밑줄은 안 된다. `legacy` 같은 예약 ID와 이미 쓰는 ID는 안 된다. 예: `school-a`.
   - 표시 이름: 영문·숫자·공백·`( ) _ . -`만, 첫 글자는 영문이나 숫자, 1~64자. 한글은 안 된다. 예: `School A`.
4. 등록 목록 표의 상태는 **검토 대기** 또는 **게시됨 vN**이다. **검토 열기**를 누르면 **검토·게시** 탭으로 간다.
   - 잘못 등록했으면 **삭제**에서 ID를 그대로 입력해 확인하고, 다른 ID로 다시 등록한다. 등록·검토·게시 내용, 사전·확장 항목·시험 질의 기준은 지워지고 **되돌릴 수 없다**. 평가 기록은 남는다.

### 검토·게시 탭에서 할 일

1. 맨 위 **검토자**에 DB를 만든 사람의 이름을 넣는다. 브라우저가 기억하며, 사전·게시·기준 저장에 함께 쓴다.
2. **항목 연결 검토 시작**을 누른다.
3. **AI 추천 모두 승인**을 누르고 확인창의 **승인**을 누른다. 대기 중이고 추천이 있는 항목만 승인하며, 게시하지는 않는다. **승인 뒤 표를 꼭 훑어본다.** 이름만 보고 학년 칸을 개설 연도로 오인하거나, 수강 기록 table의 학기를 강좌 학기로 고를 수 있다. 개설 연도는 현재 표에 없지만 이런 이름 오인은 다른 항목에도 생긴다.
4. 틀린 줄은 **다시 정하기 → 다른 칸으로**에서 table·칸을 고르고 사유를 적어 **저장**한다. 처음 값은 현재 연결된 칸이다. 정보가 없으면 **이 DB에 없음**에서 사유를 적고 **확인**한다. 추천 없는 대기 줄도 직접 정한다.
5. 게시가 막히면 **막힌 이유**의 항목·이유·할 일을 본다. 두 항목이 같은 칸을 쓰면 남길 항목을 정하고 다른 쪽은 **이 DB에 없음**으로 둔다. 숫자·시간이 글자 칸에 섞인 `3-2-2`, `09:00-10:15` 등은 게시 검사에서 막힌다. 지원하는 숫자·시간 칸으로 연결하거나, 정해진 변환이 없으면 사유를 적어 **이 DB에 없음**으로 둔다.
6. **값 사전**에 코드값의 뜻(예: GE = 교양)과 학교 줄임말(예: 소웨 = 소프트웨어학부), 필요한 교시표를 넣는다.
   - **다른 DB 사전 가져오기**: 출처를 골라 **가져오기**. 대상 칸에 실제로 있는 값만 가져온다.
   - **코드표에서 가져오기**: DB 안 코드표의 코드·이름 칸을 골라 가져온다.
   - **약어 후보(규칙)** 또는 **약어 후보(규칙+AI)**: 후보를 확인해 넣는다. 학교 고유 줄임말은 AI가 잘 못 맞히므로 직접 확인한다.
   - 넣은 뒤 **사전 적용해 게시**를 눌러야 챗봇에 반영된다.
7. 필요하면 **확장 항목**에 공통 항목에 없는 이 DB만의 정보(예: 강의실)를 넣는다. 선택 사항이다.
8. 아직 게시하지 않았다면 **검토한 항목 연결 게시**를 누른다. **사전 적용해 게시**도 게시를 수행한다. 게시 후 **시험 질의**를 열어 조회를 골라 **실행**하고, 결과가 맞으면 **기준으로 저장**한다. 이후 **회귀 확인**으로 결과가 바뀌었는지 비교한다.
9. **사용할 DB**에서 게시한 DB를 선택해 챗봇을 확인한다. 모델을 고를 수 있고 기본은 **일반 모델**이다. 이해하지 못한 낱말은 답 위에 알림으로 나온다(ADR-102). **이해한 조건 (QueryIR)**과 결과를 함께 보고 판단한다. **평가 질문 자체를 미리 물어 보지는 않는다.**

## 4. 질문 파일 쓰기

`.schema-adaptive/blind-evals/<평가 ID>/questions.json` (예: `.schema-adaptive/blind-evals/school-a-v1/questions.json`). 이 폴더는 git에 올라가지 않는다.

```json
{
  "format": "blind-eval-questions-v1",
  "database_id": "school-a",
  "author": "팀원 이름",
  "fixed_at": "2026-10-10",
  "questions": [
    {"id": "a01", "text": "컴공 전공필수 과목 보여줘", "expect": {"codes": ["CS101", "CS205"]}},
    {"id": "a02", "text": "강의실이 공학관인 수업", "expect": "decline"}
  ]
}
```

- 정답 `codes`는 그 질문에 나와야 하는 과목 코드 전체다. 자기 DB에서 SQL로 뽑는다. 1~150개다.
- `"decline"`은 그 DB에 없는 정보라서 "답할 수 없다"가 맞는 질문이다.
- 질문은 학생이 실제로 칠 법한 말로 쓴다. 약어·띄어쓰기·조건 여러 개를 섞어도 된다.
- 다 쓰면 형식만 확인한다. 이 명령은 질문 내용을 보여 주지 않는다.
  ```bash
  python -m backend.adaptive.evaluation.blind_eval check school-a-v1
  ```

## 5. 실행

```bash
python -m backend.adaptive.evaluation.blind_eval run school-a-v1
```

```bash
python -m backend.adaptive.evaluation.blind_eval report school-a-v1
```

- 챗봇 모델을 고를 수 있다(Phase 9-08). 없으면 서버의 기본 모델(일반 모델)이 답한다.
  - 두 모델을 비교하려면 같은 평가 ID로 한 번씩 실행한다.
  - 처음 것이 첫 실행, 다음 것은 재실행으로 기록된다. 결과 파일에는 답한 모델의 id와 이름이 남는다.
  ```bash
  python -m backend.adaptive.evaluation.blind_eval run school-a-v1 --model general
  ```
  ```bash
  python -m backend.adaptive.evaluation.blind_eval run school-a-v1 --model legacy-tuned
  ```
- 첫 실행 때 질문 파일이 잠긴다. 그 뒤 질문을 고치면 실행이 거부된다. 질문을 바꾸려면 새 평가 ID를 쓴다.
- 결과 파일(`run-001.json` …)에는 질문마다 PASS/FAIL/CAPPED/ERROR와 개수만 남는다. 결과 행 자체는 남지 않는다.
- QueryIR과 직접 SQL 비교(`python -m backend.adaptive.evaluation.direct_sql_pg run --set blind:<ID> --database <ID> --model general`)는 Claude/개발자가 돌린다. 팀원이 할 일은 아니다.
