# L4 사용성 점검: 진행자 안내

> AI가 준비한 자료다. 점검은 팀이 진행하고, 통과 판단도 사람이 한다. 이 문서만으로 L4가 끝난 것이 아니다.
> 관문 정의: [human-validation-checkpoints.md](../human-validation-checkpoints.md)의 L4. 2026-10-01 사용자 결정(ADR-086)으로 L4는 개발에 참여하지 않은 사람 몇 명이 써 보는 것으로 유지한다.

## 1. 목적

개발에 참여하지 않은 사람이 처음 화면을 보고 다음을 할 수 있는지 본다.

- 원하는 수업을 자기 말로 물어 찾는다.
- 챗봇이 질문을 **어떻게 이해했는지**("이해한 조건") 읽고, 결과를 믿어도 되는지 판단한다.
- "정보가 없습니다", "값을 찾지 못했습니다", "이해하지 못했습니다" 같은 답을 보고 다음 행동을 정한다.
- (관리자 과제) 처음 보는 DB를 등록하고, 검토 화면의 말(항목, 승인, 이 DB에 없음, 게시)을 이해한다.

가장 중요하게 볼 것은 **위험 행동**이다. 잘못된 결과를 맞다고 믿고 그대로 쓰려는 경우다.

## 2. 참가자

- 3~5명. 이 프로젝트의 개발이나 질문·정답 작성에 참여하지 않은 사람.
- 학생 과제: 수강신청을 해 본 학생이면 된다. 2명 이상 권장.
- 관리자 과제(선택): DB나 엑셀 표를 다뤄 본 사람 1~2명. 학생 과제를 먼저 한 사람이어도 된다.
- 한 사람에 40분 안팎(관리자 과제를 더하면 60분).
- 참가자는 P1, P2 …로만 적는다. 이름·학번·연락처는 기록하지 않는다.

## 3. 준비 (진행 전날까지)

1. 한 PC에서 [demo-procedure.md](../demo-procedure.md) 1절대로 서버를 켠다(`npm run dev:all`).
   - `backend/.env`에 **`SHOW_SQL=0`**을 넣는다. 최종 사용자 화면이 대상이므로 SQL 패널을 숨긴다.
   - adaptive 상태 줄에서 `ollama=enabled`, `pg_registration=enabled`를 확인한다.
2. 학생 과제 DB: 화면의 **DB 변경**에서 `Legacy DB (QueryIR)`를 고르고 **적용**한다.
   - 공개 수강편람으로 만든 팀 DB다(ADR-086). 학교 밖에 공개하는 자료가 아니므로 화면을 그대로 써도 된다.
3. 관리자 과제를 한다면: [demo-procedure.md](../demo-procedure.md) 2-1절의 준비대로 지어낸 학교 DB(`other_school`)를 만들고 `PG_SOURCE_OTHER_SCHOOL`을 넣어 서버를 다시 켠다. **등록은 하지 않은 상태**로 둔다(참가자가 한다).
4. 진행자가 직접 학생 과제 S1~S2를 한 번씩 해 보고, 모델이 응답하는지(첫 응답은 느릴 수 있음) 확인한다. 결과 화면은 닫는다.
5. 로그인은 하지 않는다. 참가자 계정을 만들지 않는다.
6. 관찰 기록 양식([observation-template.csv](observation-template.csv))을 복사해 `.schema-adaptive/l4/<날짜>/`에 둔다. 이 폴더는 git에 올라가지 않는다.
7. 화면 녹화는 기본으로 하지 않는다. 하려면 참가자에게 먼저 묻고, 녹화 파일도 `.schema-adaptive/l4/`에만 둔다.

## 4. 진행 순서

| 시간 | 할 일 |
| --- | --- |
| 3분 | 소개 대본(5절)을 읽는다. 동의를 받는다. |
| 25분 | 학생 과제 S1~S8([participant-tasks.md](participant-tasks.md))을 한 장씩 준다. |
| (20분) | 관리자 과제 A1~A4(선택). |
| 7분 | 사후 질문([questionnaire.md](questionnaire.md)). |
| 5분 | 진행자가 관찰 기록을 정리한다(참가자가 간 뒤). |

## 5. 소개 대본 (그대로 읽어도 된다)

> 오늘은 수강 정보를 찾아 주는 챗봇을 써 보시는 시간입니다. 시험이 아니라 **화면을 시험하는 것**이라 틀려도 괜찮고, 막히는 곳이 바로 저희가 고칠 곳입니다.
> 과제 카드를 한 장씩 드릴게요. 평소 말투로 물어보시면 됩니다. 하시면서 생각나는 것을 소리 내어 말씀해 주시면 큰 도움이 됩니다.
> 저는 되도록 도와드리지 않고 지켜보겠습니다. 정말 막히면 "넘어갈게요"라고 하셔도 됩니다.
> 이름이나 학번은 적지 않고, 입력하신 질문과 화면에서 헷갈린 점만 기록합니다. 화면 데이터는 예전 학기 공개 수강편람으로 만든 것이라 실제 이번 학기와 다를 수 있습니다.
> 시작해도 될까요?

## 6. 진행할 때 지킬 것

- 질문 문장을 알려 주지 않는다. "어떻게 물어보면 돼요?"에는 "평소처럼 물어보세요"라고만 답한다.
- 참가자가 결과를 보고 "됐다"고 하면, **"찾은 결과가 맞다고 생각하시는 이유가 있나요?"**라고 한 번 묻는다. 이해한 조건을 읽는지 보려는 것이다.
- 도와준 경우(힌트를 준 경우) 기록의 "개입"에 무엇을 말했는지 적는다.
- 개인정보(이름·학번·수강 이력)를 입력하려 하면 멈추고 다른 예로 바꾸게 한다.
- 모델 응답이 30초 넘게 오지 않으면 기다리게 하고, 시간이 초과되면 다시 묻게 한다. 기록에 "응답 지연"으로 적는다.

### 기록 칸 ([observation-template.csv](observation-template.csv))

| 칸 | 적는 것 |
| --- | --- |
| `participant`, `task` | P1, S1처럼 |
| `result` | `완료` / `도움완료` / `포기` |
| `seconds` | 과제를 시작해 끝낼 때까지 걸린 초(대략) |
| `questions_typed` | 입력한 질문 그대로. 이름·학번이 들어가면 지운다 |
| `confusion` | 헷갈린 곳(화면 위치와 참가자의 말) |
| `intervention` | 진행자가 도와준 말. 없으면 비운다 |
| `risky_belief` | 틀린 결과나 엉뚱한 결과를 맞다고 믿었으면 `예` |
| `severity` | `치명` / `주요` / `사소`([summary-template.md](summary-template.md) 3절 기준) |
| `note` | 응답 지연, 오류 문구 등 |

## 7. 과제별 관찰 요점 (진행자만 본다)

참고 결과는 개발 중 같은 DB에서 본 것이다. 모델 답은 실행마다 다를 수 있으니 정답표로 쓰지 말고 이상한 답을 알아보는 데만 쓴다.

| 과제 | 볼 것 | 개발 중 참고 |
| --- | --- | --- |
| S1 학과 전공 과목 | 학과 이름을 어떻게 쓰는지(정식 이름, 줄임말, 띄어쓰기). 결과 수와 이해한 조건을 보는지. | "컴융 전공 과목 보여줘" → 82건, 학과명 = 공과대학 컴퓨터융합학부, 이수 구분에 "전공" 포함 |
| S2 요일·오전 | "오전"을 어떻게 쓰는지. 시간 조건이 카드에 보이는지 확인하는지. | "월요일 오전 수업 보여줘" → 200건(최대 표시), 시작 시간 < 12:00 |
| S3 복합 조건 | 조건 여러 개 중 빠진 것이 있을 때 알아차리는지. | 조건을 빠뜨릴 수 있다(알려진 한계). 이해한 조건과 비교해 보는지가 핵심 |
| S4 과목이 열리는 곳 | "강의실 정보가 없어 답할 수 없습니다"를 보고 이해하는지, 다음에 무엇을 하는지. | 이 DB에는 강의실 항목이 없다 |
| S5 교수님 수업 | 교수 이름 입력(성만, 이름 전체, "교수님" 붙임). | 이름 일부도 찾는다(포함 검색) |
| S6 주말·늦은 시간 | 0건이나 "값을 찾지 못했습니다"를 보고 "그런 수업이 없다"로 이해하는지, "챗봇이 못 알아들었다"로 이해하는지. | 0건일 때 어느 조건이 맞지 않았는지 알려 줄 수 있다(같음·포함 조건 4개 이하일 때만) |
| S7 추천 요청 | 개인 상황 추천은 지원하지 않는다. 그 답을 보고 실망·혼란이 큰지, 질문을 바꾸는지. | "질문을 이해하지 못했습니다" 또는 엉뚱한 검색이 나올 수 있다. 엉뚱한 결과를 추천으로 믿으면 **위험 행동** |
| S8 이해한 조건 설명 | 결과가 나온 질문의 이해한 조건을 자기 말로 설명할 수 있는지. 용어("포함", "≥")를 이해하는지. | 새 질문을 보내면 조건 카드는 지워지고, 답이 없으면 카드가 생기지 않는다. 대화 기록의 "QueryIR 실행 완료: N건. 이해한 조건: …" 문장에는 남아 있다. 참가자가 그 문장을 찾는지도 본다 |
| A1 등록 | 연결·schema·Database ID·Label 입력에서 막히는지. AI 제안을 20~30초 기다리는지. | ID는 영문 소문자·숫자·하이픈, Label은 영문·숫자·공백·`( ) _ . -`만 된다. 한국어 Label은 거절된다 |
| A2 검토 | 항목 이름(예: 대상 학년, 분반)과 column 이름을 맞춰 보는지. AI 제안을 그냥 승인하는지. | AI가 대상 학년을 학기 코드로 잘못 고르는 경우가 있었다(8-18) |
| A3 약어 | 값 사전에서 줄임말을 넣는 곳을 찾는지. | `소웨` → 소프트웨어학부 |
| A4 게시와 질문 | 게시 뒤 DB를 바꾸고 줄임말로 질문해 결과를 확인하는지. | "소웨 전공필수 과목 보여줘" |

## 8. 알려진 한계 (참가자가 물으면 설명, 먼저 말하지 않음)

- 한 번에 한 질문만 이해한다. 앞 질문을 이어서 "그중에서"라고 하면 앞 조건이 남지 않는다.
- 조건이 많으면 하나를 빠뜨릴 수 있다. 이해한 조건 카드로 확인해야 한다.
- 개인 상황(내 시간표 빈 시간, 남은 학점)을 해석하는 추천은 하지 않는다.
- 시간: 앞말 없는 1~7시는 오후로 읽는다(예: "3시" → 15:00, 8-25). QueryIR 화면의 질문 작성 가이드에도 그렇게 적혀 있다.
- 데이터는 예전 학기 공개 수강편람이다. 이번 학기와 다를 수 있다.

## 9. 끝난 뒤

1. 참가자마다 관찰 기록을 정리하고 사후 질문 답을 같은 폴더에 둔다.
2. 관리자 과제를 했다면 다음 참가자 전에 등록을 지운다. 게시한 DB는 켜 있는 서버의 메모리에 남으므로 **서버를 끄고** 지운 뒤 다시 켠다.
   1. 서버를 끈다(Ctrl+C).
   2. 참가자가 쓴 Database ID(예: `school-a`)의 폴더를 지운다.
      ```bash
      rm -rf .schema-adaptive/postgres-registrations/school-a .schema-adaptive/postgres-profiles/school-a
      ```
      `legacy-base`·`legacy-view`는 지우지 않는다.
   3. 서버를 다시 켜고, DB 변경 목록에 그 DB가 없는지 확인한다.
3. 모든 참가자가 끝나면 [summary-template.md](summary-template.md)로 요약을 만든다. 요약에는 개인정보와 교수명을 쓰지 않는다. 요약만 `docs/l4-usability/results-<날짜>.md`로 저장소에 올린다.
4. 통과 판단(고칠 것을 고쳤는지, 한계로 남길 것을 적었는지)은 사용자와 팀이 한다. 관문 기록 줄을 요약 끝에 적는다.
