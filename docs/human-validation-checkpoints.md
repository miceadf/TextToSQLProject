# 사람·사용자 검증 체크포인트

> 작성: 2026-09-14 · 상태: 팀 공유용 초안 · 기준: `schema-adaptive-text-to-sql-plan.md`

## 목적과 현재 경계

자동 테스트는 코드가 **정의된 계약대로** 작동하는지 검사한다. 질문의 실제 뜻, 대학별 컬럼·코드값의 업무 의미, 개인정보 사용 권한, 사용자 신뢰도, 논문 주장까지 승인하지는 못한다. AI가 구현과 테스트를 함께 작성하면 같은 가정 오류가 양쪽에 들어갈 수도 있다. 사람 검토는 개발 중 모든 단계의 필수 중단점이 아니라, 해당 결과를 사용·공유·주장하기 전의 승인 관문이다.

2026-09-28 상태: SQLite 합성 fixture 3개는 같은 6개 개설강좌의 구조 변형이다. 공통 질문 40개는 전부 `NEEDS_HUMAN_REVIEW`다. `FakeModel` oracle smoke는 실제 모델 성능이 아니다. 합성 clarification 화면과 session 범위 DB 변경(flat·legacy-schema의 동일 canonical 목록·질의)은 실제 Chrome browser smoke를 통과해 내부 팀 논의에 쓸 수 있지만 L4 사람 검토는 미수행이다. 파일 DB의 private quarantine 등록, loopback upload, mapping 검토·명시적 publish, strict activation 뒤 registry/catalog/clarification 편입은 합성 자동 테스트로 검증했으나 이 전체 흐름의 실제 browser smoke는 미수행이다. 이 합성 publish는 실제 학교 DB의 의미 검토나 L2 승인이 아니다. PostgreSQL inspector·QueryIR compiler·AST policy·read-only executor, server-owned backend registry/catalog/clarification routing, Git 비추적 private startup profile과 별도 DSN 환경변수의 CLI 주입, frontend strict registry 선택은 자동 검증했다. 확인된 clarification constraint로 기존 Ollama adapter의 semantic context를 제한하는 provider와, loopback CLI option으로만 이를 켜는 server-owned startup 설정(proxy·redirect 차단 transport)도 synthetic transport와 로컬 임시 server로 자동 검증했다. Phase 7-09에서 로컬 Ollama에 완전 합성 질문 4건을 prototype 전체 경로로 보내 호출 예산·응답 shape·redaction 경계를 확인했으나, 모델 출력은 4건 모두 reflection guard에서 거부되었다. 이 실행은 모델 내장 CNU SYSTEM이 주입된 조건이었고, Phase 7-10에서 요청 형식을 명시해 재실행한 결과 2건이 성공 실행 경로를 live로 통과했다(0행, 불필요한 filter 경향 잔존). 이는 모델 성능 검증이 아니며 L1/L3 전 수치로 쓰지 않는다. 직접 SQL 비교군과 QueryIR의 paired 비교 계약은 oracle 자기 일관성(120/120)까지 자동 검증했으며, Phase 5-19 비교는 모델 내장 CNU SYSTEM이 주입된 조건이라 정정했고, 이를 제거한 Phase 5-20 잠정 비교(IR 정답 93/120, 직접 SQL 72/120)도 gold 40건 L1 검토와 L3 결과 검토 전에는 잠정치이며, 이 수치를 논문에 쓰기 전 L1·L3가 필요하다. Phase 5-21 base instruct 실행(SQL 90/120, IR 0/120)은 arm 간 code fence 추출 규칙 비대칭 때문에 방식 비교로 쓰지 않고, 대칭 규칙을 적용한 Phase 5-22 재실행(fine-tune IR 93·SQL 72, base IR 78·SQL 90)을 기준으로 하되 이 역시 L1/L3 전 잠정치다. Phase 5-23에서 모델 비교 주장을 schema 변화에 대한 정확도 일관성으로 한정했고, 같은 seed의 합성 변형 2종(coded·hybrid)을 더한 5종에서 IR arm은 두 모델 모두 variant별 정답 수가 같고 직접 SQL arm은 JOIN이 필요한 schema에서 떨어졌다. 5종 모두 개발자가 만든 합성 schema이고 fixture mapping도 개발자 작성이므로 L2(mapping 검토)·E4/L6(독립 unseen schema)·L1/L3를 대신하지 않는다. Phase 8-01에서 합성 private SQLite의 mapping 버전 이력·이전 버전 재활성화를 자동 검증했다. 재활성화도 실행 권한 변경이므로 실제 학교 DB에서는 publish와 같이 L2 뒤에만 쓰며, 관리자 화면의 사용성은 L4 대상이다. Phase 8-02의 등록 간 schema 비교는 구조 metadata만 대조하는 읽기 전용 기능이며, 이름이 같아도 의미가 바뀐 column이나 코드값 변화는 잡지 못하므로 실제 DB의 승계 판단은 L2 검토를 대신하지 않는다. Phase 8-03의 승계는 구조가 같은 field를 사유와 함께 REMAP할 뿐이므로, 실제 학교 DB에서는 승계 field도 L2에서 의미를 다시 확인해야 한다. 승계로 줄어드는 관리자 작업량은 합성 조건의 관찰이며 사용자 평가(L4) 전 결론이 아니다. Phase 8-04의 test query 미리보기는 게시·활성 mapping의 실제 행 값을 관리자 화면에 최대 5행 보여주므로, 실제 학교 DB에서는 연결 전 L2, 실데이터 시연·공유 전 L5를 그대로 적용한다. Phase 8-05의 verified 기준선은 관리자가 결과를 확인했다는 기록일 뿐 결과의 의미가 맞다는 승인(L2)이나 gold 검토(L1)가 아니며, 회귀 `MATCH`는 기준선과 같다는 뜻이지 정답이라는 뜻이 아니다. 실제 PostgreSQL profile을 띄운 browser end-to-end smoke, Ollama 실통합, 실제 학교 DB, 독립 unseen school은 아직 검증되지 않았다. 루트 `pytest`의 legacy `backend/test_correction.py` import 오류는 별도 기준선 결함으로 남아 있다. 각 수치는 해당 시점 기록이지 향후 통과 보증이 아니다.

사용자 확인(2026-09-29): legacy 서비스의 PostgreSQL 강좌 DB는 충남대 수강신청 테이블을 그대로 가져온 것이 아니라 팀이 유사한 스키마와 데이터로 직접 구성한 것이다. 사용자는 legacy와 스키마 적응 prototype을 함께 실행하는 팀 내부 공유(`npm run dev:all`)에서 실제 데이터 노출을 고려하지 않아도 된다고 밝혔다. 이 확인은 legacy 강좌 DB에 대한 사실 기록이며, 기존 CNU 학습 데이터셋(5,385 SQL)·가명 artifact의 E3와 외부 시연 L5 판단을 AI가 대신 승인한 것이 아니다.

Phase 7-12(2026-09-29): legacy 챗봇의 대상 view를 QueryIR 경로에 부분 mapping으로 등록했다. mapping은 12개 field이고, 미지원 3개와 학점·시간 변환을 포함한다. legacy DB에는 읽기 전용으로 연결해 schema inspection, profile 작성, 고정 query smoke를 실행했고, 구조와 집계만 기록했다. 이 mapping은 개발자가 작성했다. legacy 강좌 DB가 팀 구성 데이터라는 사용자 확인에 근거한 개발용 등록이며, 실제 학교 DB의 L2 mapping 검토를 대신하지 않는다. 변환 목록(`SLASH_FIRST_NUMERIC`, `TIME_TO_HHMM`)이 실제 학교 DB의 값 형식에 맞는지는 L2에서 다시 확인한다.

Phase 7-13(2026-09-29): legacy view 대상 QueryIR 챗봇 endpoint를 추가하고, 로컬 Ollama와 legacy DB로 8개 질문을 live 실행했다(상태·행 수만 기록). 이 실행은 동작 확인이며 L1/L3 전의 모델 성능 근거가 아니다. 모델이 문자열 field에 구절 전체를 `equals`로 넣는 경향을 server 규칙으로 완화할지는 7-15 비교 뒤 사용자가 결정한다.

Phase 7-14(2026-09-29): `npm run dev:all`이 legacy backend의 `backend/.env` DB·Ollama 설정을 재사용해 QueryIR 챗봇 경로를 켠다. 화면의 `DB 변경`에서 `Legacy DB (QueryIR)`를 고르면 AI Course Assistant가 QueryIR 경로로 답한다. 팀 내부 비교용 개발 경로이며, 외부 시연(L5)이나 사용성 평가(L4)를 대신하지 않는다.

Phase 7-15(2026-09-29): legacy 챗봇과 QueryIR 경로를 개발자 작성 30문항으로 비교했다. 기준 SQL과 한국어 의미 해석(예: `오전`=12시 이전)은 개발자 판단이며 gold가 아니다. 결과 문서의 수치를 팀 공유 외 용도(논문·성능 주장)로 쓰기 전에 L1 문항·기준 검토와 L3 결과 검토가 필요하다. 후속 서버 정책(limit, 문자열 `contains` 완화, 코드값 정규화, field 별칭, 학년 등 ontology 확장)은 사용자·팀 결정 대기다.

Phase 7-16(2026-09-29): 사용자 결정으로 챗봇 서버 정책 3종(limit 200, 이름형 문자열 `contains`, 요일 정규화)을 적용하고 같은 30문항으로 재비교했다. ONTOLOGY 범위 수용 가능 문항은 QueryIR 14, legacy 17이다. 이 수치도 개발자 작성 문항·기준의 잠정치이며 L1·L3 전이다.

Phase 7-17(2026-09-29): legacy DB 기본 table에 기준 table 보존 LEFT JOIN으로 매핑한 `legacy-base`를 추가했다. view 경로와 전체 관계·30문항 답이 같음을 개발자 검증으로 확인했다. 이 mapping도 팀이 구성한 legacy DB에 대한 개발자 작성이며 L2 검토가 아니다.

Phase 8-06(2026-09-30): legacy 두 profile에 이수구분 값 사전(실제 값 9개와 괄호 없는 표기)을 개발자가 선언했다. 실제 학교 DB의 코드값 의미는 L2에서 검토해야 하며, 이 사전은 그 승인을 대신하지 않는다.

Phase 8-08(2026-09-30): 합성 변형 benchmark(12개 변형, 정답 mapping, gold QueryIR 20개)는 개발자 작성이다. AI mapping 제안 비교 결과를 논문이나 성능 주장에 쓰기 전에 L1(질문·기준)과 L3(결과) 검토가 필요하다.

Phase 8-09(2026-09-30): AI mapping 제안 비교(AI 223/240, 규칙 205/240)는 개발자 작성 합성 benchmark 위의 한 번 실행이다. 논문·성능 주장 전에 L1·L3가 필요하다. 실제 DB에 AI 제안을 쓰려면 L2 검토가 필요하다. 특히 AI가 틀린 의미 함정(학년 column, 강의실 정원)은 사람 검토로만 잡힌다.

Phase 8-10(2026-09-30): 보류 변형과 관리자 설명(`admin-notes-v1`)은 개발자가 규칙에 따라 작성했다. 실제 관리자가 쓰는 설명의 형태와 양은 다를 수 있다. 설명 효과에 대한 주장(자연어 설명 무효, 코드표 유효) 전에 L1/L3가 필요하다.

## 2026-10-01 사용자 결정: 데이터 전제와 관문 재정의

**전제.** 실제 학교 DB를 받아 오는 것은 사실상 불가능하다. 그래서 평가와 개발은 다음 데이터만으로 한다.
- **레거시 DB:** 팀이 이전 학기 수강편람 엑셀로 구성했다. 학생들에게 공유된 파일을 내려받아 만들었다. 실제 학교 데이터이지만 학교가 학생에게 공개한 강좌 정보이고, 학생 개인정보는 없다.
- **흉내 낸 DB:** 다른 학교 수강 정보를 참고해 우리가 만든 DB.
- 실제 학교 자료를 따로 받게 되면 사용자가 알린다. 그때 이 결정을 다시 본다.

| 관문 | 결정 |
| --- | --- |
| E3 | 기존 학습 데이터셋과 레거시 DB는 공개 수강편람 기반으로 사용한다. 원본 엑셀과 DB 덤프는 공개된 곳(공개 저장소, 웹)에 올리지 않는다. 논문에는 집계만 쓴다. |
| L5 | 시연은 자유롭게 하고, 개발 옵션의 SQL 표시도 켜도 된다. 데이터가 흉내 낸 것인지 공개 수강편람 기반인지 밝힌다. 학교 밖에 공개하는 자료(공개 README, 블로그 등)의 화면에서는 교수명을 가린다. |
| L2 | 별도 관문이 아니라 제품 기능이다. 관리자 화면의 검토 → 승인/"이 DB에 없음" → 게시가 곧 의미 검토이고, 그 DB를 만든 사람이 검토한다. 레거시·합성 DB mapping에 "L2 아님"을 덧붙이지 않는다. |
| L1/L3 | 사용자가 먼저 검토하고 팀원도 검토한다. AI는 검토 표만 준비한다. 표는 Phase 9 진입 때 팀원이 만든 평가 질문과 함께 준비한다. |
| L4 | 그대로. 개발에 참여하지 않은 사람 몇 명이 써 본다. |
| E4/L6(독립 학교) | 팀원이 다른 대학의 공개 수강편람·시간표를 참고해 2~3개 학교 DB를 흉내 내어 만든다. 규칙은 다음과 같다. ① 학교명·교수명은 지어낸다. ② 평가 질문과 정답은 DB를 만든 사람이 먼저 고정한다. ③ AI(개발자)는 평가 전까지 그 DB와 질문을 보지 않는다. ④ 첫 실행 결과를 그대로 기록하고, 그 뒤 수정은 따로 표시한다. ⑤ 논문 한계에 "모든 평가 데이터는 모사 데이터"라고 적는다. AI가 만든 8-17 가상 학교는 개발용이며 독립 학교를 대신하지 않는다. |
| 공통 ontology | 사용자가 결정하면 확정이다(팀 공유는 선택). 8-18의 대상 학년(버전 2)은 확정이다. |

이 표는 사용자가 결정한 것을 기록한 것이다. AI가 스스로 관문을 승인한 것이 아니다. 개인정보 보호 장치(접속 정보 비노출 등)는 이미 만든 것을 유지하되 추가 투자는 하지 않는다. 아래의 이전 기록에 있는 "E3/L5 판단 필요", "L2 아님", "SQL 표시를 끈다" 같은 문구는 이 결정으로 대체된다.

Phase 9-09(2026-10-12): ChatGPT API 선택지와 값 힌트(질문에 나온 레거시 DB 값) 전송은 사용자 결정이다(ADR-099). 외부로 가는 데이터 범위가 바뀐 것이므로 시연·논문 자료에서 출처와 함께 밝힌다. L5 규칙(교수명 처리)은 그대로다.

Phase 9-08(2026-10-12): 적응형 챗봇의 기본 모델을 일반 모델로 바꾼 것은 사용자 결정이다(ADR-098).
- 두 모델의 비교 수치(레거시 30문항 23 대 22, `other_school` 10/12 대 12/12, 리허설 6/14 대 6/14)는 개발자가 고정한 질문과 AI가 만든 DB 위의 잠정치다.
- 모델 우열이나 적응성의 근거로 쓰지 않는다. 팀원 DB 평가를 두 모델로 각각 실행해 다시 본다.
- L1/L3 승인 상태는 바꾸지 않았다.

Phase 9-06(2026-10-10): 리허설 재실행 9/14·오류 0은 문제를 본 뒤 고친 재실행 결과다. 개발용 수치이며 적응성 근거가 아니다.

Phase 9-05(2026-10-08): 리허설 학교 재실행 9/14는 문제를 본 뒤 고친 결과라 "재실행"으로 기록했다. 개발용 수치이며 적응성 근거가 아니다. 레거시 확인 36/36 불변은 개발자 작성 질문 기준이다(L1 전).

Phase 9-04(2026-10-08): 리허설 학교 `rehearsal_school`과 질문 14개는 AI가 만든 개발용이다. 첫 실행 6/14는 적응성 근거가 아니며 E4/L6를 대신하지 않는다.

Phase 9-03(2026-10-06): 팀원용 환경 점검 명령(`python -m backend.adaptive.env_check`)은 L7 준비용이다. 이 명령의 통과는 L7(새 환경에서 전체 테스트·화면·통합 재현) 통과가 아니다.

Phase 9-02(2026-10-06): L4 진행 자료를 [l4-usability/](l4-usability/facilitator-guide.md)에 준비했다. L4는 아직 진행하지 않았다. 참가자 섭외·진행·통과 판단은 팀이 하고, AI는 L4를 승인으로 표시하지 않는다.

Phase 8-25(2026-10-06): 시간 표현 규칙과 시간 질문 7개·정답은 AI가 만든 개발용이다. 결과(19/19, 18/19, 19/19)는 L1/L3 전 잠정치다. "질문 이해 개선은 L1 뒤" 원칙의 예외는 사용자가 결정했다. L1 질문 세트를 받으면 시간 표현 사례를 다시 본다.

팀 논의 자료(2026-10-06): [team-discussion-brief-2026-10-06.md](team-discussion-brief-2026-10-06.md)는 팀에게 부탁할 일(L1 판정, 평가용 DB, L3, L4)과 정할 것을 모은 것이다. 어떤 관문도 승인하지 않았고, 모든 수치는 L1/L3 전 잠정치로 적었다.

Phase 8-23(2026-10-06): AI mapping 제안 개선 수치(55→75/80)는 AI가 만든 개발용 schema와 정답 위의 것이다. 적응성 주장에는 쓰지 않는다. 팀원 DB 평가(E4/L6)와 L3에서 다시 본다. 제안이 좋아져도 관리자 검토(L2 역할)는 그대로 필수다.

Phase 9 진입(2026-10-06): L1 검토 표를 준비했다. 대상은 합성 benchmark 70개다. 파일은 [l1-review/fixture-v1-review.md](l1-review/fixture-v1-review.md)(읽기)와 같은 이름의 CSV(판정 입력)다. 판정은 사용자 먼저, 그다음 팀원이 한다. 기록 명령은 판정 형식만 확인한다. gold의 `NEEDS_HUMAN_REVIEW`는 사람이 정하기 전까지 그대로 둔다. 아직 아무 사례도 판정되지 않았다.

Phase 8-22(2026-10-06): 독립 학교 평가(E4/L6) 규칙 ②~④를 지키는 실행 도구와 팀원용 안내([teammate-evaluation-db-guide.md](teammate-evaluation-db-guide.md))를 만들었다. 팀원 DB와 질문 파일은 아직 없다. AI는 질문 파일을 평가 실행 전까지 열지 않는다.

Phase 8-21(2026-10-02~06): `wide_school`·`code_school`·`period_school`·`packed_school`은 AI가 만든 개발용 합성 DB이며 팀원 평가 DB를 대신하지 않는다(ADR-086). 결과(11/12, 14/14, 11/13, 13/13)는 L1/L3 전 잠정치다.

Phase 8-20(2026-10-01): 공통 항목 밖 개념 목록(`outside-concepts.yaml`, 11개)은 AI가 고른 개발용 데이터다. 공통 ontology를 바꾸지 않으므로 사용자 결정 대상은 아니다. L1 질문 세트를 받으면 사용자와 팀원이 목록을 보강할 수 있다. 확인 결과(레거시 9/9, 가상 학교 14/14)는 L1/L3 전 잠정치다.

Phase 8-18(2026-10-01): 공통 ontology 버전 2(대상 학년 추가)는 팀 관리 대상이라 팀 논의 때 공유가 필요하다. 레거시 확인은 로컬 확인용 서버에서만 했다. 결과는 L1/L3 전 잠정치다.

Phase 8-17(2026-09-30): 다른 학교 DB는 지어낸 합성 데이터라 E3 대상이 아니다. 고정 질문 11/12는 L1/L3 전 잠정치이며 모델 성능 주장에 쓰지 않는다.

Phase 8-16(2026-09-30): 시연 절차([demo-procedure.md](demo-procedure.md))는 팀 레거시 DB로 로컬에서만 돌렸다. 외부 시연이나 실제 학교 자료 사용 전에 L5/E3 판단이 필요하고, SQL 표시는 끈다.

Phase 8-07 축소판(2026-09-30): 값 사전과 약어는 관리자가 넣는 DB별 데이터이며, AI 약어 후보는 로컬 모델이 만든다. 실제 학교 DB의 약어를 넣을 때 L2 검토 대상이다(기록만 하고 막지 않는다).

Phase 8-15(2026-09-30): 서버 연결 목록에 실제 학교 DB 연결을 넣고 화면에서 등록하면 schema 구조와 저장 값 예시(AI 제안용, 저장하지 않음)가 로컬 모델에 들어간다. 실제 학교 DB를 연결하기 전에는 L2/E3 판단이 필요하다(기록만 하고 막지 않는다).

Phase 8-14(2026-09-30): 개발 옵션이 켜져 있으면(dev launcher 기본) 챗봇 화면에 실행 SQL, 물리 table·column 이름, 값이 보인다. 외부 시연이나 실제 자료 사용 전에는 `SHOW_SQL=0`으로 끄거나 L5/E3 판단을 받는다.

Phase 8-13(2026-09-30): 사용자 결정으로 실제 학교 데이터 노출 방지를 당분간 고려 대상에서 뺐다. 챗봇은 등록된 DB의 실제 값(학과명 등)을 로컬 모델 prompt에 넣는다. 실제 CNU 자료에 쓰거나 외부 시연하기 전에 E3/L5 판단이 필요하다. 레거시 약어 표를 옮긴 값 사전은 개발자 작성이며 L2 검토가 아니다.

Phase 8-12(2026-09-30): 업로드 DB의 mapping 초안을 로컬 모델이 정렬한다. 저장 값 예시는 loopback 모델 prompt에만 들어간다. 실제 DB를 업로드할 때 이 점이 E3 판단 대상이다. AI 제안의 정확도 주장은 L1/L3 전에는 하지 않는다.

## 개발 중 요청할 수 있는 짧은 중간 점검

사용자나 팀원은 어느 단계에서든 “현재 구현 근거, 통과한 테스트, 미검증 가정, 내가 직접 확인할 1~3개 항목”을 요청할 수 있다. AI는 완료된 기능과 미실행 환경을 구분하고, 새 기능이 ontology·mapping·gold·개인정보·논문 결론에 영향을 줄 때 검토 대상을 먼저 알려야 한다. 기계적 회귀 검사는 AI가 수행할 수 있지만, 사람 승인 상태를 AI가 대신 변경하지 않는다.

## 검토 기록 최소 양식

`ID / 대상 버전·fingerprint / 검토자(팀 역할) / 검토일 / 확인 방법 / 승인·수정·보류 / 이슈 ID 또는 수정 커밋 / 재검토 필요 여부`

기록에는 실제 질문·SQL·학생 정보·비밀키를 불필요하게 복사하지 않는다. 검토 전후에 gold·mapping·정책이 바뀌면 이전 승인과 측정 수치를 자동 승계하지 않는다. 미완료 항목은 완료로 체크하지 않고 다음 관문에 남긴다.

## Phase 9-10 메모 (2026-10-12 사용자 결정, ADR-100)

평가 전용 PostgreSQL 직접 SQL 비교군을 만든다. 사용자는 catalog·column별 예시 10개/40자·실제 값 힌트를 허용했다. 같은 날 OpenAI 평가 허용을 철회했다(추가 비용 없음; ChatGPT Plus는 API 사용량을 포함하지 않음). OpenAI 측정과 직접 SQL OpenAI 경로는 제외하고 로컬 `general`로만 비교한다. 관리자 mapping·변환·값 사전은 직접 SQL에 쓰지 않는다("등록만" 비용 비교). 제품 챗봇은 ADR-099 범위 그대로다.

개발 질문 56개(레거시 30, other_school 12, rehearsal_school 14)는 QueryIR 규칙을 맞춘 질문이라 A(QueryIR)에 유리하다. 판정 근거는 팀원 DB와 고정 질문의 첫 실행이다. 에이전트는 팀원 질문을 평가 전에 보지 않는다. 구현 때 가짜 모델·전송 targeted 테스트를 실행했고, 9-10c에서 제공된 Luna 리뷰 지적 4건을 재현·고쳤다. 이번 문서 기록은 새 모델 호출(Luna/opencode 포함)·측정·서버 조작·테스트 없이 수행한다. 어떤 관문도 승인하거나 사람 검토를 완료로 바꾸지 않는다.

2026-10-12 사용자 승인으로 한 번 측정한 로컬 7B 결과: 직접 SQL 17/56·QueryIR 42/56(레거시 10/30·26/30, other_school 5/12·10/12 — QueryIR은 9-08 재사용, 리허설 2/14·6/14). [결과 문서](phase9-10-direct-sql-results-2026-10-12.md). **개발 질문·L1/L3 전 잠정치, 관문 승인 없음.** 제품 구조 변경 결정도 내리지 않았다.
